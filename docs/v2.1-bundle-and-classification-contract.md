# NetSniper v2.1 Bundle and Host-Classification Contract

Status: Stage 0E contract baseline.

## 1. Compatibility boundary

NetSniper v2.1 remains a CLI/headless telemetry sensor. DeltaAegis remains the
operator interface.

The existing v2.0 bundle remains the outer compatibility boundary. v2.1 adds:

- a required `capability_manifest` object to finalized v2.1 bundles;
- a required v2.1 host-classification object for every emitted host; and
- deterministic legacy projections for consumers that understand only the v2.0
  fields.

No v2.0 field may be silently removed or redefined. The v2.1 objects are
authoritative when present.

## 2. Capability manifest

The capability manifest records what the sensor requested, what it completed,
what failed, and what it could not perform.

Required areas:

- sensor, classifier, taxonomy, evidence-profile, and bundle versions;
- requested and normalized target scope;
- scan profile and privilege context;
- discovery methods;
- tool versions;
- per-collector status and reason codes;
- inventory counts;
- artifact paths, sizes, and hashes; and
- finalization and integrity state.

Collector failures, unavailable collectors, and skipped collectors must include
a controlled reason code. They must never be represented as successful empty
results.

A v2.1 bundle passes host-retention policy only when:

```text
discovered_host_count == emitted_host_count
omitted_host_count == 0
host_inventory_preserved == true
```

## 3. Host-classification object

Every emitted host receives one
`netsniper-host-classification-v2` object containing:

- identity confidence and observed identity keys;
- device-family result;
- zero or more role results;
- platform result;
- observation quality;
- evidence records;
- missing-evidence records; and
- a legacy projection.

Device family, roles, and platform are independent axes. A role may be
classified while family remains unknown. A host may have multiple classified
roles.

## 4. Evidence provenance

Every scored or contradictory observation receives a unique evidence ID.

Classification results reference evidence IDs rather than duplicating raw
scanner output. Each evidence record states:

- affected axes;
- source type;
- collector;
- reliability;
- positive, negative, contradiction, or contextual effect;
- observation timestamp;
- normalized value; and
- optional raw-artifact reference.

Raw references are bundle-relative evidence pointers. They must not permit path
escape from the finalized run directory.

## 5. Missing evidence and negative evidence

Collector failure, unavailability, or profile omission is explicit
`missing_evidence`.

Missing evidence is not negative evidence. A partial scan must set
`negative_evidence_allowed` to false unless the classifier can prove that the
specific negative observation came from a completed collector with adequate
coverage.

A partial scan may lower confidence and create uncertainty reasons, but it must
not claim that an uncollected service, platform, or protocol is absent.

## 6. Decisions and confidence

Canonical decisions are:

- `classified`
- `possible`
- `review`
- `unknown`

Canonical bands are:

- `none`: 0
- `weak`: 1–39
- `possible`: 40–69
- `strong`: 70–89
- `high`: 90–100

Decision and confidence band remain separate. A strong contradiction forces
review even when the unadjusted score was high.

Unknown, possible, and review outcomes contain controlled uncertainty reasons.

## 7. Legacy projection

The legacy projection preserves:

- `primary_type`
- `device_type`
- `device_type_confidence`
- `confidence`
- `confidence_label`
- `decision`
- `secondary_candidates`
- `contradictions`
- `calibration_reason`

It is derived from the authoritative v2.1 result. Runtime code must not score the
legacy projection independently.

Historical `contradiction_review` is permitted only inside the compatibility
projection. The canonical v2.1 decision is `review`.

## 8. Bundle invariants

The v2.1 implementation must enforce:

1. Every finalized v2.1 bundle has exactly one capability manifest.
2. Every emitted host has exactly one v2.1 classification object.
3. Every referenced evidence ID exists in the same host object.
4. Evidence IDs are unique within a host object.
5. Collector IDs in host evidence exist in the capability manifest.
6. Collector-state sets do not overlap.
7. A completed collector cannot carry a failure reason.
8. A failed, unavailable, or skipped collector carries a reason code.
9. Bundle artifact paths are relative and confined.
10. The same normalized evidence and contract versions produce the same result.
11. A strong contradiction prevents `classified` for the affected candidate.
12. Port-only, vendor-only, and hostname-only confidence caps remain enforced.
13. Unknown/review controls cannot become classified through legacy projection.
14. The compatibility projection cannot be more confident than its
    authoritative source result.
15. Discovered hosts are never silently omitted.

## 9. Contract examples

The contract directory contains:

- a complete capability manifest;
- a partial capability manifest;
- a multi-role Linux compute-host classification; and
- a contradiction-driven review classification.

The examples are specification fixtures. They are not evidence that the current
v2.0 runtime already emits the v2.1 contract.
