# NetSniper v2.1 Stages 1–2 Implementation

Status: development implementation on `feature/v2.1-evidence-calibration`.

## Runtime authority

NetSniper v2.1 uses `netsniper_core.classifier.classify_host` as the single
authoritative classification implementation. Live analysis, bundle enrichment,
and fixture validation all invoke that implementation. `netsniper.sh` now
orchestrates data collection and artifact finalization; it no longer contains an
independent device-scoring table.

Machine-readable scoring data remains in
`classification/evidence_profiles.json`. The file contains canonical
`device_family`, `role`, and `platform` axis profiles plus the legacy profile
section retained for historical validators.

## Analysis flow

1. Nmap grepable and XML evidence is normalized.
2. Exposure findings are emitted independently of device classification.
3. The authoritative classifier produces identity, family, role, platform, and
   observation-quality results.
4. A deterministic legacy projection populates existing v1/v2 compatibility
   fields.
5. Full inventory preservation runs before bundle finalization.

## Bundle additions

Every finalized v2.1 bundle adds:

- `capability_manifest.json`
- `host_classifications.json`
- `analysis.enriched.json`
- `classification_quality.json`
- `classification_quality.md`

The existing `netsniper-run-v3` manifest remains the outer contract and retains
`netsniper-run-v2` compatibility metadata. The manifest records the v2.1
capability, classification, classifier, taxonomy, and evidence-profile contract
versions.

## Safety behavior

- Port-only, vendor-only, and hostname-only evidence cannot exceed confidence
  39.
- A single non-unique high-reliability source cannot exceed confidence 69.
- Strong conflicting candidates force `review`.
- Service roles do not infer a device family.
- Missing collectors are explicit and are not negative evidence.
- Accurate scans missing requested OS or UDP-lite evidence remain valid partial
  telemetry rather than pretending the evidence was collected.
- Discovered and emitted host counts must match before finalization.

## Validation

Run:

```bash
./tools/validate_v2_1_stage1_2_all.sh
```

The gate validates the v2.1 contracts and classifier behavior, then executes the
NetSniper v2.0 functional compatibility suite.

## Policy-alignment correction before corpus activation

The first implementation checkpoint is followed by a narrow policy-alignment
correction before any corpus fixture becomes active.

The correction enforces the Stage 0 contract:

- confidence 0 produces `unknown`;
- confidence 1–39 produces `review`;
- confidence 40–69 produces `possible`;
- confidence 70–100 produces `classified`;
- caps and ambiguity thresholds are read from
  `classification/evidence_profiles.json`;
- collector failure and unavailability are copied into canonical uncertainty
  reasons; and
- legacy review output distinguishes weak/review-only evidence from a genuine
  strong contradiction.

The development, evaluation, and regression split assignments remain frozen.
No fixture is activated by this correction.

## Deterministic development and regression corpus

The follow-on corpus checkpoint activates the 14 development and 4 regression
fixtures described in `docs/v2.1-corpus-activation.md`. The 12 evaluation
fixtures remain planned and are excluded from calibration. The complete gate
now includes deterministic corpus replay before historical compatibility tests.
