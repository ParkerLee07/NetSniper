# NetSniper v2.1 Stages 1–2 Implementation

Status: development implementation on `feature/v2.1-evidence-calibration`.

## Runtime authority

NetSniper v2.1 uses `netsniper_core.classifier.classify_host` as the single
authoritative classification implementation. Live analysis, bundle enrichment,
and deterministic fixture validation all invoke that implementation.
`netsniper.sh` orchestrates data collection and artifact finalization; it does
not contain an independent device-scoring table.

Machine-readable scoring data remains in
`classification/evidence_profiles.json`. The file contains canonical
`device_family`, `role`, and `platform` axis profiles plus the legacy profile
section retained for historical validators.

## Analysis flow

1. Nmap grepable and XML evidence is normalized.
2. Exposure findings are emitted independently of device classification.
3. The authoritative classifier produces identity, family, role, platform, and
   observation-quality results.
4. A deterministic legacy projection populates existing v1/v2 compatibility
   fields.
5. Full inventory preservation runs before bundle finalization.

During live analysis, `netsniper.sh` streams a local route-context snapshot
directly to the analyzer using `ip -4 route get` and
`ip -4 route show default`. The Python analyzer accepts a default-gateway
observation only when the target route uses one unambiguous interface, one
best-metric IPv4 gateway uses that interface, and the gateway lies inside the
authorized target scope. Route context is not written into the run directory or
archived.

## Bundle additions

Every finalized v2.1 bundle adds:

- `capability_manifest.json`;
- `host_classifications.json`;
- `analysis.enriched.json`;
- `classification_quality.json`; and
- `classification_quality.md`.

The existing `netsniper-run-v3` manifest remains the outer contract and retains
`netsniper-run-v2` compatibility metadata.

## Safety behavior

- Port-only, vendor-only, and hostname-only evidence cannot exceed confidence
  39.
- Sub-threshold hostname-only platform evidence remains a secondary candidate;
  the canonical platform stays `unknown`.
- Generic TCP/443 does not independently support `security_gateway` or
  `hypervisor`; distinctive product, title, VPN-protocol, or dedicated
  management-port evidence remains required.
- Default-gateway context is local, observational, target-scoped,
  interface-matched, and ambiguity-safe. It adds no network probe.
- A single non-unique high-reliability source cannot exceed confidence 69.
- Strong conflicting candidates force `review`.
- Service roles do not infer a device family.
- Missing collectors are explicit and are not negative evidence.
- Accurate scans missing requested OS or UDP-lite evidence remain valid partial
  telemetry.
- Discovered and emitted host counts must match before finalization.

## Deterministic test framework

The v2.1 classifier is protected by 14 development and 4 regression fixtures.
They are ordinary saved-input software tests and are replayed on every complete
gate. There is no formal evaluation holdout, candidate seal, one-time replay,
or statistical accuracy process.

The three authorized real-device scans are documented separately as manual,
non-statistical characterization in
`docs/v2.1-real-world-characterization.md`. They are not committed as raw or
sanitized corpus inputs.

## Validation

Run:

```bash
./tools/validate_v2_1_stage1_2_all.sh
```

The gate validates classifier contracts, deterministic corpus behavior,
observation integrity, the embedded-administration boundary, the observed-behavior
corrections, and NetSniper v1.9 and v2.0 compatibility.
