# NetSniper v2.1 Deterministic Classification Gates

Status: conventional development and regression test policy.

## Purpose

NetSniper v2.1 uses a compact deterministic test corpus to protect classifier
behavior. These files are engineering tests, not a statistical benchmark and
not a replacement for real-world operational validation.

The repository does not maintain a formal evaluation holdout, candidate seal,
one-time replay authorization process, or statistical accuracy program for
v2.1.

## Test splits

Every active corpus case belongs to one of two ordinary software-test splits:

- `development`: representative inputs used while implementing and reviewing
  classification behavior.
- `regression`: inputs that permanently protect a known compatibility behavior,
  safety boundary, or corrected defect.

The v2.1 corpus contains exactly:

- 14 development cases; and
- 4 regression cases.

All 18 cases are active and replayed by the standard validation gate.

## Release-blocking deterministic gates

The following checks must pass exactly:

- deterministic replay rate: 100%;
- host-retention rate: 100%;
- schema-validity rate: 100%;
- required uncertainty-reason compliance: 100%;
- confidence-cap compliance: 100%;
- strong-contradiction review behavior: 100%;
- legacy-projection match rate: 100%;
- fixture expectation pass rate: 100%;
- false high-confidence classifications: 0; and
- unknown controls incorrectly emitted as classified: 0.

These values describe test-suite conformance only. They are not a measured
real-world accuracy percentage.

## Real-world characterization

Authorized real-device scans may be reviewed separately to identify practical
limitations or candidate defects. Raw captures and identifying network data are
not committed to the corpus. A real observation becomes a permanent regression
case only when a specific behavior needs deterministic protection and the case
is independently reviewed and sanitized.

See `docs/v2.1-real-world-characterization.md` for the current non-statistical
characterization notes.

## Accuracy claims

The 18-case deterministic corpus does not justify a public percentage-accuracy,
precision, recall, or calibration claim. NetSniper v2.1 documentation may state
that the declared regression, compatibility, safety, and bundle-integrity gates
pass. It must not convert test pass rates into claims about population-level
classification accuracy.

## Release readiness

NetSniper v2.1.0 release candidates must satisfy the following boundaries:

1. all 18 deterministic cases must remain active and referenced;
2. every exact corpus gate must pass;
3. observation-integrity, embedded-administration, and observed-behavior
   regressions must pass;
4. generic HTTPS must not create specialized security-gateway or hypervisor
   roles;
5. route-derived gateway evidence must remain local, scoped, interface-matched,
   and ambiguity-safe;
6. hostname-only sub-threshold platform evidence must leave the canonical
   platform unknown;
7. v1.9 and v2.0 compatibility suites must pass;
8. real-world characterization findings must be reviewed without unsupported
   statistical claims; and
9. the complete gate must pass from a clean checkout.

### Empirical calibration gate

`tools/validate_v2_1_empirical_calibration.py` verifies deterministic reports, optional separated ground truth, privacy-safe corpus intake, and the no-automatic-weight-change boundary.

### DeltaAegis evidence-enrichment gate

`tools/validate_v2_1_deltaaegis_enrichment.py` verifies additive compatibility, axis attribution, fingerprint stability, and gate wiring.

## Final release validation

Before requesting approval to stage and commit the release-finalization changes,
review the exact diff and run the focused behavioral and metadata validators. The
release-finalization commit requires prior operator approval.

After that approved commit leaves the feature branch clean, run the authoritative
release-candidate command:

```bash
./tools/validate_v2_1_release_gate.sh
```

This gate composes the deterministic classifier and corpus checks, observation
integrity, embedded-administration and observed-behavior boundaries, empirical
calibration safeguards, additive DeltaAegis enrichment, and the v1.9/v2.0
compatibility suites. Passing the gate does not authorize a push, merge, tag, or
GitHub Release; each remains a separate operator-approved action.
